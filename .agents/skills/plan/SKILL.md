# 先出计划，批准后再动手

## 什么时候要计划

按风险和波及面判断，不按改动行数：

- **小**：只动一个模块，行为改变一眼能验证，出错容易回退（改文案、修一个有复现的 bug、加一条测试）。不写计划，直接做。
- **中**：跨进程或跨模块（渲染进程 ↔ preload ↔ IPC ↔ 主进程 ↔ omp），改用户可见的流程，或碰到数据、配置文件、子进程生命周期。写计划。
- **大**：改协议处理、任务引擎、安装/更新/打包、安全边界（preload 暴露面、IPC 校验、`~/.omp` 写入），或者要做 `AGENTS.md`「先停下来问」里的事。写计划，并把要问的事列进待定问题。

拿不准就按大一级算。

## 先调查再写

读 `AGENTS.md`、涉及功能的 `docs/architecture/<功能>.md`、`docs/design/spec.md` 对应章节和相关代码，弄清现状。能用工具查到的事不留给仓库所有者回答。

## 计划格式

短，一屏能看完；每项一两行：

```
## 目标
<用户能观察到的结果，一两句>

## 不做
- <明确排除的范围>

## 切片
1. <切片名>：<改什么，涉及哪些文件/模块>
   验收：<命令（npx vitest run …、npx playwright test test/e2e/…）、要看到的断言或界面结果>
2. …

## 风险
<小/中/大> — <最可能出错的地方，出错的后果>

## 待定问题
- <需要仓库所有者决定的事，附选项和你的倾向>
```

切片要求：

- 每片单独做完就能验证、能提交，不依赖后面的切片才能编译或测试通过。
- 验收写具体：哪条命令、哪个 spec、断言什么；改界面写在哪种窗口宽度和语言下看什么（e2e 断言，不拍截图交差）。
- 顺序按依赖排，先做风险最大、最能证伪方案的那片。

## 等批准

把计划发给仓库所有者，**批准前不改文件**（读代码、跑只读命令可以）。批准时改了范围就按改后的做；执行中发现计划不成立，停下来说明原因和新方案，再等确认。
